از راه‌اندازی صفر تا کنترل دقیق Offset در Production

این سند خلاصه‌ی کامل مسیری‌ست که طی کردیم: از بالا آوردن یک کلاستر Kafka با Docker، تا فهم عمیق Producer/Consumer، معماری داخلی مدیریت Offset، امن‌سازی با SASL/ACL، و چک‌لیست رخدادهای واقعی روزمره برای یک تیم که روی زیرساخت پیام‌رسانی مالی کار می‌کند.

🐳 Docker + KRaft 🔐 SASL/PLAIN → SASL_SSL ☕ Java Client 🏦 Financial-grade concerns

01 راه‌اندازی با Docker

یک کلاستر تک‌نودی با حالت KRaft (بدون نیاز به Zookeeper) — کافی برای یادگیری و تست کامل عملیاتی.

# docker-compose.yml
services:
  kafka:
    image: apache/kafka:3.7.0
    container_name: kafka
    ports:
      - "9092:9092"
      - "9093:9093"
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      CLUSTER_ID: "MkU3OEVBNTcwNTJENDM2Qk"
docker compose up -d
docker exec -it kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
نکته فلگ -it فقط برای اجرای تعاملی مستقیم در ترمینال است. هرگز داخل اسکریپت، حلقه، یا جایی‌که خروجی pipe/parse می‌شود از آن استفاده نکنید — باعث ورود فریم‌های کنترلی داکر به stdout و داده‌های به‌ظاهر بی‌معنی می‌شود.

02 مفاهیم پایه: Topic, Partition, Replica, ISR

پایه‌ی تمام تصمیمات بعدی — از طراحی Topic تا عیب‌یابی Under-Replication.

Partition

یک Topic فقط یک اسم است؛ داده‌ی واقعی در پارتیشن‌ها (صف‌های مستقل و ترتیب‌دار) ذخیره می‌شود. ترتیب پیام‌ها فقط درون یک پارتیشن تضمین می‌شود، نه در کل Topic.

Replica

هر پارتیشن می‌تواند چند نسخه روی بروکرهای مختلف داشته باشد: یک Leader (تمام خواندن/نوشتن از اینجا) و چند Follower که فقط رپلیکیت می‌کنند.

ISR — In-Sync Replicas

لیست رپلیکاهایی که کاملاً با Leader سینک هستند. تنظیم acks=all یعنی «تا وقتی همه‌ی اعضای ISR (نه لزوماً همه‌ی Replica) تایید نکنند، موفق حساب نکن». min.insync.replicas کف ایمنی این ISR را تضمین می‌کند.

Topic: orders  PartitionCount: 3  ReplicationFactor: 3
  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
  Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
  Partition: 2  Leader: 3  Replicas: 3,1,2  Isr: 3,1   ← بروکر ۲ عقب افتاده!

03 Producer: مسیر پیام، Partitioner، Idempotence

هرچیزی که برای تضمین تحویل درست و بدون تکرار پیام لازم است.

مسیر یک پیام

Serializer → Partitioner → بافر داخلی (RecordAccumulator) → Sender thread → بروکر. اگر key بدهید، همیشه به یک پارتیشن ثابت می‌رود (تضمین ترتیب برای آن Key)؛ بدون Key از Sticky Partitioner استفاده می‌شود.

سطوح تضمین تحویل

سطحتنظیمپیامد
At-most-onceacks=0سریع، ممکن است پیام گم شود
At-least-onceacks=all, retries=MAXگم نمی‌شود، ممکن است تکراری شود
Exactly-onceenable.idempotence=trueبدون تکرار، بدون گم‌شدن (در سطح Producer)

چطور Idempotence واقعاً کار می‌کند

هر Producer یک PID و Epoch می‌گیرد. هر پیام برای هر پارتیشن یک Sequence Number ترتیبی دارد. بروکر آخرین Sequence موفق هر (PID, Partition) را نگه می‌دارد؛ اگر یک batch با Sequence تکراری برسد (نتیجه‌ی retry شبکه‌ای)، بدون نوشتن مجدد، فقط offset قبلی را برمی‌گرداند.

محدودیت مهم Idempotence فقط جلوی duplicate ناشی از retry در یک Producer session را می‌گیرد؛ نه duplicate ناشی از restart کامل اپلیکیشن یا چند Producer جدا که یک پیام را دوبار می‌فرستند. برای آن سطح تضمین، باید Idempotency Key منطقی در سطح دامنه (business logic) پیاده‌سازی شود. 
props.put("acks", "all");
props.put("enable.idempotence", "true");
props.put("retries", Integer.MAX_VALUE);
props.put("max.in.flight.requests.per.connection", 5);
props.put("linger.ms", 20);
props.put("compression.type", "lz4");

04 Consumer Group و Offset

Offset متعلق به Topic نیست — متعلق به رابطه‌ی بین یک Group و یک Topic/Partition است.

Offset = f(Group, Topic, Partition) Topic: orders (partition 0) ├── billing-group → current offset: 5000 └── analytics-group → current offset: 3200 (کاملاً مستقل از هم)

کامیت دستی (اصولی برای production)

props.put("enable.auto.commit", "false");

05 معماری داخلی: __consumer_offsets

قلب اصلی موضوع — همه‌ی عملیات Reset در واقع فقط نوشتن یک رکورد جدید در این Topic داخلی است.

  • یک Topic داخلی با معمولاً ۵۰ پارتیشن (offsets.topic.num.partitions)
  • cleanup.policy=compact — فقط آخرین مقدار هر Key نگه داشته می‌شود
  • Key: (group_id, topic, partition) — Value: (offset, metadata, commit_timestamp)
  • پارتیشن مسئول یک Group: hash(group_id) % offsets.topic.num.partitions
  • Leader آن پارتیشن = Group Coordinator همان Group
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server <host:port> --consumer.config /tmp/client.properties \
  --topic __consumer_offsets \
  --formatter "org.apache.kafka.tools.consumer.OffsetsMessageFormatter" \
  --from-beginning --max-messages 20
ریسک Retention اگر یک Group بیش از offsets.retention.minutes (پیش‌فرض ۷ روز) غیرفعال بماند، Offset ذخیره‌شده‌اش کامل پاک می‌شود. رفتار بعدی به auto.offset.reset بستگی دارد.

06 کنترل و برگرداندن Offset (Reset / Seek)

مسیر امن: dry-run → بررسی → execute → تایید نهایی.

پیش‌نیاز اجباری گروه باید در وضعیت Empty باشد (هیچ Consumer فعالی نداشته باشد)، وگرنه خطای Assignments can only be reset if the group is inactive می‌گیرید. 
# همیشه اول Dry-run
kafka-consumer-groups.sh --bootstrap-server <host> --command-config client.properties \
  --group <GROUP> --topic <TOPIC> --reset-offsets --shift-by -100 --dry-run

# سپس Execute
kafka-consumer-groups.sh ... --reset-offsets --shift-by -100 --execute
سناریوفلگ
پردازش مجدد کامل--to-earliest
نادیده گرفتن Lag فعلی--to-latest
رفتن به Offset مشخص--to-offset 1500
عقب/جلو رفتن N پیام--shift-by -100 / 100
بازگشت بر اساس زمان (DR)--to-datetime 2026-09-13T10:00:00.000
فقط یک پارتیشن--topic orders:0
نکته حیاتی محاسباتی «۱۰۰ تا برگرد» یعنی ۱۰۰ واحد در هر پارتیشن جداگانه، نه مجموع کل Topic. با ۳ پارتیشن، عملاً حدود ۳۰۰ پیام دوباره پردازش می‌شود.
پیش از هر Reset روی سیستم مالی بپرس اگر این پیام‌ها دوباره پردازش شوند، منطق Consumer Idempotent هست؟ اگر نه، پردازش مجدد می‌تواند یعنی دوبار واریز/تسویه.

08 Cleanup Policy: delete در برابر compact

سه مقدار ممکن: delete، compact، یا هر دو با هم.

delete (بر اساس زمان/حجم، واحد Segment): [msg1][msg2][msg3][msg4][msg5] └─ کل segment قدیمی یکجا حذف می‌شود، نه پیام‌به‌پیام compact (بر اساس Key): key=A:v1 key=B:v1 key=A:v2 key=B:v2 key=A:v3 ↓ بعد از Compaction: key=B:v2 key=A:v3

delete

مناسب event log و تراکنش‌های تاریخچه‌دار مثل fund-transfer. کنترل با retention.ms / retention.bytes.

compact

مناسب changelog وضعیت مثل __consumer_offsets. کنترل با min.cleanable.dirty.ratio و Tombstone (value=null).

هشدار Migration تغییر cleanup.policy از delete به compact روی Topic پرشده، تاریخچه‌ی چند-نسخه‌ای هر Key را به‌مرور از بین می‌برد. هرگز روی Topic تراکنشی که تاریخچه‌اش مهم است این کار را نکنید.

۱۰ امن‌سازی: Authentication، ACL، Encryption

سه لایه‌ی مستقل — نبود هرکدام یعنی یک شکاف امنیتی واقعی، نه فرضی.

وضعیت رایج مشاهده‌شده SASL_PLAINTEXT + PLAIN یعنی احراز هویت هست ولی رمزنگاری نیست — پسورد به‌صورت base64 ساده روی شبکه رد و بدل می‌شود و با Sniffing قابل خواندن است. برای production باید به SASL_SSL مهاجرت شود.

Authorization (ACL) — لایه‌ای که اغلب فراموش می‌شود

خطای SecurityDisabledException: No Authorizer is configured یعنی هیچ ACL ای وجود ندارد — هر یوزر Authenticate‌شده، دسترسی کامل به همه‌چیز دارد.

# فعال‌سازی (server.properties هر بروکر)
authorizer.class.name=org.apache.kafka.metadata.authorizer.StandardAuthorizer
super.users=User:admin
allow.everyone.if.no.acl.found=true   # برای Migration تدریجی، سپس false

# تعریف دسترسی Produce
kafka-acls.sh --add --allow-principal User:payment-service \
  --operation Write --operation Describe --topic fund-transfer

# تعریف دسترسی Consume (نیازمند اجازه روی Topic و Group)
kafka-acls.sh --add --allow-principal User:reporting-service \
  --operation Read --topic fund-transfer --group reporting-group

مسیر پیشنهادی Migration بدون قطعی

  1. شناسایی همه‌ی Client های متصل به هر Topic (Consumer Groups + JMX/netstat برای Producer)
  2. اطمینان از یوزر مجزا برای هر سرویس (نه یک یوزر مشترک)
  3. فعال‌سازی Authorizer با allow.everyone.if.no.acl.found=true
  4. تعریف تدریجی ACL دقیق برای هر سرویس شناسایی‌شده
  5. سوییچ نهایی به false و Rolling Restart

۱۱ رخدادهای روزمره: Admin در برابر Developer

چک‌لیستی واقع‌گرایانه برای هر دو نقش، در dev و production.

ADMIN / DEVOPS

Under-Replicated Partitions، Rebalance Storm، دیسک پر، Broker Down، Unclean Leader Election، Quota برای Client پرمصرف، انقضای گواهی TLS.

DEVELOPER

Poison Pill message، Deserialization Exception، OffsetOutOfRange، Duplicate processing (نبود Idempotency)، Schema Breaking Change.
